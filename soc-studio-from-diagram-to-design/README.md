# SoC Studio：让芯片设计，走出文件的孤岛

简体中文 | [English](README.en.md)

![封面：SoC Studio：让芯片设计，走出文件的孤岛](assets/generated/cover-zh.png)

*从可视化集成出发，构建连接 IP、系统设计、代码生成与验证的工程工作台。*

> **这是一个正在开发中的项目，不是成熟产品的发布宣言。** 本文既介绍当前已经落地的能力，也展开 SoC Studio 的完整产品愿景；“规划”“目标”“未来”所描述的能力不代表今天已经可用。当前 Aurora 已有非 EDA 源码集成的自动验证记录，尚未完成 RTL 编译、仿真、综合或启动验证。

给 SoC 加一个 UART，听起来是件小事。

找到 IP，接上总线，分配一段地址——然后呢？时钟从哪里来，复位由谁控制，中断占哪个编号，引脚经过 PINMUX 还是交给上层？如果它需要生成代码，还得确认脚本用的是哪份配置，以及输出目录里那份 RTL 到底是不是这一次生成的。

你并不是不会做这些事。恰恰相反，你太熟悉了：打开几个文件，对照一张表，跑一段脚本，再回到顶层检查一遍。

麻烦在于，系统的完整模样，往往只存在于那个同时记住所有细节的人脑中。

**我们想把它拿出来。**

这就是 SoC Studio 的起点：一个运行在浏览器中的 SoC 集成工作台，让 IP、参数、连接与生成过程，围绕同一份工程组织起来。

我们不是要让工程师少写几行代码，而是想减少一种更隐蔽的成本：**同一个设计决定，被人在多个地方重复表达、反复核对。** 地址改了，生成脚本是否知道？参数变了，端口定义是否跟上？项目交给另一个人，他能否分辨哪份输出仍然有效？

SoC Studio 当前做的事情，就是先把这些对应关系变成明确、可保存、可检查的数据。它的价值不是“拖几个方框就造出芯片”，而是让错误有机会更早暴露，让 IP 更容易复用，让交接不再完全依赖口头解释，也让后续自动化有可靠的输入。效率提升需要在真实项目中衡量，我们不预设一个漂亮的百分比。

## 为什么把这样的工具放进浏览器？

不是因为浏览器能替代 EDA，而是因为设计者不应该为了理解同一个系统，不断切换入口。

画布适合看关系，表单适合做配置，表格适合检查地址，日志适合追踪失败。网页可以把这些不同的表达方式放在一个工作台里：从模块进入参数，从连线进入端点，从生成任务进入结果。我们看重的是这种连贯性，而不是简单地把桌面窗口搬上网页。

另一个原因，是把**人在哪里操作**与**工具在哪里执行**分开。浏览器负责交互，后端负责工程存储、校验、脚本和工具调用。今天，它们可以都运行在自己的电脑上；未来，计算和许可证资源可以留在指定的工作站或服务器，设计者通过受控的入口访问。后者需要鉴权、隔离、调度与审计，是规划，不是当前本机服务已经具备的能力。

这种分离也给 GUI 之外的工作方式留下空间。同一套工程能力，应当既能由鼠标调用，也能由 Tcl、命令行和 CI 调用；浏览器不应该成为自动化的边界。

因此，“网页化”不意味着零安装、不意味着 RTL 在浏览器里运行，更不意味着必须把设计交给云端。当前仍需安装后端与工具依赖，工程可以保存在本地。它是一种架构选择：让交互入口更统一，让执行环境可以独立演进。

## 画一根线很容易。让它算数，才是难题

如果你用过 Vivado 的 Block Design，应该熟悉那种工作节奏：找到一个 IP，放进设计，双击配置，再把接口连起来。

SoC Studio 借鉴的是这种连续的设计体验。但对于由不同来源 IP 和 generator 组成的系统，仅仅把方框画出来，还远远不够。

一根线必须回答：它从哪个真实接口出发，接到哪里，方向和位宽是否匹配？一次参数修改必须回答：端口会不会改变，已有连接还能不能成立？

所以，我们把画布看作工程模型的一个入口。实例绑定具体的 IP 版本，参数属于实例，地址和中断关系保存在工程中。拖动模块只改变位置；修改参数，则需要面对它带来的真实影响。

画布的意义不在于替工程画一张说明图，而在于让设计者直接触碰工程本身。

## 你要的是一条总线，不是一份写死的总线样板

设想你从 IP Repo 里选中一个 Interconnect。

你想决定它有多少个输入、多少个输出、如何连接上下游，而不是发现所谓“可配置”，只是给一组固定端口换个名字。

这让我们重新划清了 IP 与工程之间的边界：公共 Repo 保存 IP 的定义、源码和生成入口；工程保存这一次实例化的选择。生成出来的项目专属代码，也留在工程里，不反过来改写公共 IP。

普通 RTL 参数化 IP 和 generator IP 也不能混为一谈。前者的参数可能直接进入 HDL 实例，后者的配置则可能先决定生成什么代码。SoC Studio 用结构化描述承载参数类型、范围、接口及生成入口，让普通参数拥有通用表单，也为总线等复杂模块保留专用配置界面。

这里的“标准化”，指 SoC Studio 的接入契约，而不是声称支持所有现有 IP 标准。接口能否随配置变化，也必须由 IP 的真实声明与适配能力决定。

这是一种更可持续的复用方式：**复用的是 IP 的能力，而不只是某个项目留下的结果。**

## 看清系统，有时需要先少看一点

当中断、时钟、复位、告警和调试信号一起铺满画布，“完整显示”反而可能遮住最重要的问题。

你想追踪一条访问路径，看到的却是一团交叉线；你想检查一个中断源，却得先辨认几十个端口。

SoC Studio 选择按问题组织视图。看总线时，关注访问骨架；看时钟复位时，关注来源和分发；需要检查 Alert 或 Debug，再切到相应专题。它们是同一份设计的不同观察角度，不是几张需要分别维护的图。

成组信号也不必永远逐条铺开。在 ALL 视图中，符合条件的同源模块到同目标模块的中断或普通信号，可以折叠成一条带数量的汇总线。点击它，才展开真实成员、端口和编号。同一网络的多个分支，则可以一起高亮。

隐藏的是暂时不需要的细节，不是连接事实。

## 真正的考验，发生在按下 Generate 之后

一个绿色的“成功”，很容易让人安心。

但它回答了什么？脚本退出了？文件生成了？RTL 编译了？还是系统真的启动了？这些不是同一件事。

为了让 SoC Studio 面对真实复杂度，我们选择了基于 OpenTitan IP 的 Aurora 数字子系统。它不是完整 Earl Grey 的复制，而是一份有自己规模与系统边界的集成设计。

真实模块不会迁就演示：GPIO 的多位中断要逐位落到控制器输入；总线的地址窗口要进入生成配置；复位要有来源；调试授权不能因为不好连接，就随手绑成常量。每一处都在追问同一个问题：画布上的设计，和最终代码说的是不是同一件事？

目前，Aurora 已有真实 generator 执行、系统顶层生成和 FuseSoC 依赖源码导出的自动验证记录。SoC Studio 将输入快照、日志和输出组织起来；相关设计输入变化后，旧结果也会被标记为过期，而不是继续拿昨天的成功为今天背书。

这条路已经走到了源码交付，但还没有走到 RTL 编译、仿真、综合或芯片启动验证。我们不会把前者包装成后者。

**工程工具的可信度，不只在于它能宣布什么成功，也在于它能说清楚什么还没有被证明。**

## 从一个可以放心修改的设计开始

理解一个工具，最好的方式往往不是从空白页读说明，而是打开一个真实设计，问它几个问题。

这个外设接在哪里？为什么需要这条复位？如果改了配置，哪些地方会受到影响？

Aurora 以受保护的 Demo 备份提供。每次从 Demo 打开，都会在工程目录创建一份可编辑副本。你可以修改它、保存它、重新审视它，而不必担心把原始样例改得再也找不回来。副本不继承历史运行产物，也不会因为打开就执行脚本。

## 我们想做的，远不止一张 Block Diagram

前面的截图展示的是今天的开发版本。下面展开的，是完整规划：一些环节已有实现子集，一些还在打基础，还有一些需要真实 EDA 环境才能推进。它们不是一份已经交付的功能清单，而是同一段设计旅程最终应该抵达的地方。

### 从一个文件夹，走向一份可以交接的工程

我们希望工程不仅能新建、保存和重新打开，还能管理 RTL、仿真源码、约束、头文件、宏定义、编译顺序和顶层选择。复制、模板、最近工程、便携 Bundle、依赖锁定、迁移与恢复，都应该围绕同一套版本化数据工作。

这背后需要一个统一的变更内核：画布、表单与脚本提交同样的工程事务；非法操作不留下半份修改；旧版本工程有明确迁移规则；撤销、并发冲突和外部文件修改不靠猜测处理。当前已有相关实现，但入口规则收敛和完整阶段验收仍需继续。

最终，一份工程应该能回答“它由什么组成、依赖哪个版本、如何重建”，而不是只能在某个人的工作目录里打开。

### 让 IP 成为可以复用的资产，而不是复制过来的目录

公共 Catalog 的目标不只是搜索名称。开发者应当能够查看来源、许可、文件集、版本和依赖；通过 Packager 把静态 RTL、参数化 IP 或 generator IP 打包；在导入预检时发现缺文件和不支持的语义；升级之前看清影响，而不是静默替换旧版本。

参数配置也应从基础的类型、枚举、范围，继续延伸到条件参数、派生参数、接口数量与位宽、批量配置和 preset。改变参数时，工具应解释哪些端口、连接和生成结果会受影响，必要时提出需要用户确认的修复方案。

IP-XACT 与 FuseSoC 等接入会通过适配层逐步扩展；当前只支持明确子集，不承诺任意第三方描述都能无损导入。通用 IP 表单与 Interconnect、CLKMGR、PLIC 等专用编辑器，也要共同服务于真实 IP 契约，而不是各自维护一套事实。

### 从“两个端口接起来”，走向系统级设计

连接编辑的规划覆盖接口 bundle、标量信号、合法扇出、多驱动检查、重连，以及外部端口、常量、切片、拼接和显式适配组件。进一步是把一组模块封装成层级子系统，暴露边界端口和参数，打包为 CBB，在同一系统中多次实例化，并支持版本升级与局部构建。

系统资源也必须跟上：多 Master 地址空间、分配与锁定、映射与排除，以及后续的重映射、别名和访问权限；多中断控制器、源与目标、触发与极性、优先级和共享规则；时钟的来源、频率、派生与域，复位的极性、同步与关联关系，再到电源域和未来 UPF 映射。

这些目标不能被界面上的选项提前“实现”。例如，当前 Aurora 的地址生成尚不支持 Master 专属重映射、别名或权限过滤。跨时钟域、跨复位域的意图检查，也不能冒充 CDC/RDC 签核。

在此基础上，连接自动化才有意义：先提出兼容匹配、缺失桥接或资源连接的建议，说明假设和影响，再由用户审查应用。设计检查则要给出稳定的规则编号、严重度、具体对象与修复线索，允许有理由、有范围、会失效的豁免，而不是用一个“全部通过”盖住未知问题。

### 从一次生成，走向一条可追溯的构建与验证链

生成器不该是一颗只能点击、无法解释的按钮。完整目标包括依赖任务图、单 IP 与系统级输出、HDL wrapper、地址头文件、中断表和集成文档；每次运行记录输入、工具版本、命令、日志和产物摘要，并处理缓存失效、排队、取消、超时、失败、重试及历史对比。Provider 接口与 SDK 则为外部脚本和工具保留接入位置。

再往前，是验证计划：测试用例、随机种子、配置矩阵、预期输出，以及 generate → lint / elaboration → test → collect 的执行链。结果需要区分未覆盖、跳过、阻塞、失败和过期；规划中的覆盖率、JUnit/JSON 报告、波形入口、基线比较和质量门禁，都应该指向可查的执行证据。当前已有契约回归与运行管理子集，不等于这些验证能力已经完整落地。

真正的 EDA 工作由目标平台插件承接：工具和许可证环境检查、RTL 编译与仿真、约束管理、综合、IP 独立构建、增量构建与实现，以及时序、面积、利用率和功耗报告。FPGA 下载与硬件调试是可选扩展，ASIC 则对接相应平台的验证与签核流程。SoC Studio 要组织这些工具，不自行替代它们的算法，也不把 FPGA 与 ASIC 的流程混为一谈。

### 让鼠标做过的事，也能由脚本和 CI 重现

Tcl、稳定的 Command API 和无浏览器 CLI，是完整规划的一部分：查询对象、创建实例、配置参数、连接接口、分配地址，再导出和回放设计。脚本错误要能定位到具体行，失败不能只应用前半段修改，退出码和结构化输出要能接入 CI。当前 Tcl 是受限子集，不是任意 Vivado 脚本的执行环境。

我们也希望问题可以沿着同一条线索被追踪：从画布到源码，从诊断到端口，从失败报告到生成任务，再回到设计。源码与配置编辑、生成文件只读标记、差异比较、自动导出的接口/地址/IRQ 文档，以及验证需求到测试结果的追踪，都在这条路径上。

当这些基础稳定后，交付与协作才能更进一步：干净环境恢复、headless CI、产物保留策略、容器或远程 Worker、资源与许可证调度、权限和审计、凭证隔离、Git 审查与多人冲突处理，以及索引重建和备份恢复。**浏览器让远程入口成为可能，却不会自动解决团队协作和安全。** 当前服务仍是无鉴权的本机单进程开发服务，不能直接暴露到公网。

### 规模变大之后，依然能让人看懂

最后，画布不能只在演示规模下好用。规划会继续推进层级导航、局部范围与路径观察、信号聚合、按缩放层级显示细节，以及适合不同拓扑的 Interconnect 形态与路由。

键盘操作、高对比显示、窄屏适配和错误恢复同样属于工程能力。百级到千级实例的性能需要用真实测量建立预算，再经过兼容性与升级演练、完整用户旅程验收，而不是仅凭一张流畅的截图宣布达标。目前我们尚未完成这些规模化门禁。

## 现在加入，是参与把它做成，而不是等待它已经完美

SoC Studio 正处在开发阶段。当前的重点，是用 Aurora 把设计模型、真实 IP、generator 和源码交付连接起来；完整的硬件验证、跨机器环境复现与团队平台能力，还需要继续推进。本文描述的是我们要走的方向，不是对所有功能已经可用的承诺。

但我们想解决的问题已经很清楚：让工程师少花一点精力，记住那些本该由工具记住的对应关系；多留一点注意力，判断系统为什么这样设计，以及它是否正确。

如果你手里也有需要反复接入的 IP、不断演进的总线配置，或一套只有少数人能维护的集成脚本，欢迎带着它们来试试。

下一次要给 SoC 加一个 UART，我们希望你首先想到的，不再是“那几个文件在哪儿”，而是：**它应该怎样成为这个系统的一部分？**

让设计走出文件的孤岛，不是把文件藏起来，而是把它们之间的关系建立起来。这就是我们正在做的 SoC Studio。
