# E4B 权重容量：为什么不能按有效参数估算

![E4B 参数口径与资源容量的概念封面](assets/generated/cover-12-zh.png)

[系列索引](README.md) · 第 12 期

假设拿到一块可供模型使用的有限内存，看到“E4B”便按 4B 参数乘 2 字节预留空间，会在装载前就算错。名字中的 `E` 指 effective；[Google 模型卡](https://ai.google.dev/gemma/docs/core/model_card_4)给出约 4.5B effective 参数，以及约 8B 包含 embedding 的总参数。前者帮助理解每 token 的有效计算规模，后者才更接近静态权重容量的起点。主 Embedding、PLE、各层投影和多模态部分都要存；PLE 的大量表项按 token ID 查取，不会全部变成每个 token 的矩阵乘。

先做一个**理想紧凑存储的下界算术**：若总数粗取 8B 个参数，全部 BF16 每个 2 字节，约 16 GB；若全部均匀 4 bit，约 4 GB。它只是在计算参数净荷，尚未包含量化元数据、运行时副本、KV Cache 和其他工作区。实际格式也未必让每个模块都用同一种位宽。

[官方 Gemma 4 概览](https://ai.google.dev/gemma/docs/core)给 E4B 列出的装载内存估算，可以和这道算术题并排看：

| E4B 格式 | 官方装载内存估算 |
| --- | ---: |
| BF16 | 17.9 GB |
| SFP8 | 8.9 GB |
| Q4_0 | 4.5 GB |

官方表格按模型版本与量化级别估算，含约 20% 的附加装载开销；它仍**不包含上下文带来的 KV Cache**，具体工具和环境会使数字变化。概览还列出使用 LiteRT-LM 的移动版 2.5 GB、纯文本移动版 2.2 GB。这些是不同发布格式的装载估算，不能把 4 GB 的统一 4 bit 理论净荷当作其中任一格式的真实文件大小或整机峰值内存。

## 量化后，权重怎样进入计算

量化把原本较高精度的权重映射成少量离散值。常见的分组形式可写作 `w≈s(q−z)`：`q` 是低比特整数，`s` 是该组的 scale，`z` 是可能使用的零点。执行矩阵乘时，硬件既要取出打包的 `q`，也要按格式取得 scale，才能让乘加对应到原来的数值尺度。具体格式可以不用零点，也可以按通道或更小的组保存 scale；“4 bit”只说了 `q` 的宽度，没有说完整的数据布局。

例如某矩阵有 `N` 个元素，每 64 个 4 bit 值共用一个 BF16 scale，理想字节数是 `N×0.5+(N/64)×2=0.53125N`。第 10 期那张 `[2560,10240]` gate 权重若按此构造格式打包，净荷约 13.3 MiB；BF16 是 50 MiB。额外的 scale 使平均占用超过每值 0.5 字节，这里还没计零点、分组索引、对齐和未量化模块。它只是说明元数据如何进入容量账，**不是 E4B 官方 Q4_0 的格式定义**。

还要分清量化了什么。`W4A16` 表示 4 bit 权重配 16 bit 激活；权重少占存储，并不意味着激活、累加器和 KV Cache 也变成 4 bit。[Google 已提供 Gemma 4 的 QAT 发布格式](https://ai.google.dev/gemma/docs/core)，包括面向不同推理后端的 4 bit 权重格式，以及采用混合位宽和优化 KV 的 E4B 移动格式。后训练量化（PTQ）在模型训练后压缩权重；量化感知训练（QAT）则在训练中模拟量化误差，让模型有机会适应该误差。采用 QAT 仍需在目标任务上评测质量。选模型时应记录具体 checkpoint 与格式，而不只写“E4B INT4”。

## 压缩的字节，硬件有没有少搬

量化最直接的收益是降低静态权重容量。对 Decode 更关键的是带宽：第 10 期看到，单请求每步只有一行输入，一块投影权重很难被许多行分摊。在刚才构造的 gate 例子里，只计一次权重读取，单行计算的理想算术强度由 BF16 的约 `1` 升至约 `3.8` FLOP/byte。如果权重以打包形式从外存传来，在计算阵列附近按块解包并使用 scale，外存传输量才有机会随位宽下降。反过来，如果运行时先把整张低比特权重展开成 BF16 并长期放在外存，模型文件虽小，Decode 读取权重的带宽账可能又接近 BF16。

计算单元也要匹配这种数据流。有的实现把低比特权重边读边转换，再用较高精度乘加；有的设备能在低比特路径上直接计算。两者对解包吞吐、scale 读取、片上 SRAM、乘加阵列和累加精度的要求不同。因此，权重从 16 bit 降到 4 bit，不能直接推出四倍 token/s 或四倍能效；若解包或 scale 供给跟不上，计算阵列仍会空等。Prefill 有较多行可复用同一权重块，Decode 更依赖持续供给，量化收益也就要分阶段测。

PLE 和主 Embedding 又是另一种访问形态：它们的大表按 ID 取部分行，容量会随量化下降，但单步不会把整张表顺序读一遍。查表时还要看一次取出多少打包数据、scale 与表项是否一起命中缓存；把 PLE 节省的静态容量直接算作每个 token 同比例的带宽节省，会高估收益。KV Cache 则按请求和历史长度增长，其位宽需单独选择；只量化权重不会自动降低长上下文的 KV 读取量。

## 把静态参数和动态状态放到同一张账上

以**仅作算术练习**的 BF16 为例：主 Embedding 约 1.25 GiB，PLE 打包表约 5.25 GiB，二者已约 6.5 GiB；其他投影、归一化、视觉/音频参数还未计入。若只用 E4B 名称里的 4B 乘 2 字节，会与这两张表本身的数量级冲突。模型卡的 8B 总参数是近似值，并不替代逐模块统计；做装载预算，应以所用 checkpoint 的实际张量和格式为准。

动态部分与请求有关。第 11 期的 BF16 理想 KV 例子，在 128K 全局历史时，持久生产层状态已可到约 1 GiB；请求数增加时，这部分近似按请求份数增长。峰值还可能包含加载时的原格式权重、副本、量化元数据、视觉/音频前端临时激活和注意力工作区；各项是否同时存在，需按实际调度时间线判断。设备选型不能只看单份静态权重能否放下。

最后还要把质量放回选择里。权重低比特化会改变投影结果，误差可能逐层传递；KV 量化又会改变后续每步读取的历史数值。比较两种格式，要固定模型版本、量化方法、测试集和评估方法，再同时看容量、首 token 延迟、后续 token/s 与任务质量。本章没有设备或质量实测，因此这些算术和硬件分析不构成某个格式的性能承诺。下一章转向另一类数据搬运：Attention 的分数与概率中间表能否不完整写回外存。
