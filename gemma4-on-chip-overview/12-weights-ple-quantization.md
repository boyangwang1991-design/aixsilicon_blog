# E4B 权重与量化：从参数容量到芯片带宽

![E4B 参数口径与资源容量的概念封面](assets/generated/cover-12-zh.png)

[系列索引](README.md) · 第 12 期

一块设备能否装下 E4B，不能拿名字里的“4B”直接乘每个参数的字节数。这里的 `E` 指 effective：[Google 模型卡](https://ai.google.dev/gemma/docs/core/model_card_4)给出约 4.5B effective 参数，以及约 8B 含 embedding 的总参数。前者描述每个 token 的有效计算规模，后者才更接近需要存放的静态参数数。第 09 期看到的 PLE 正是两者相差很大的原因之一：它给各层备有按 token ID 查取的表项，表很大，却不会在每个 token 上与整张表做矩阵乘。

端侧选型要接着回答三个问题：这些参数和运行状态占多少空间？量化后究竟少了多少字节？芯片执行时有没有真的少搬这些字节？

## 先分清常驻权重与随请求增长的状态

只做**理想参数净荷算术**：粗取 8B 个参数，全部按 BF16 的 2 字节保存，约 16 GB；若全部均匀按 4 bit 紧凑保存，约 4 GB。它们都不是可运行 E4B 的设备内存需求，前者用了近似参数数，后者还假设每个模块都能采用同一位宽。

E4B 的表项说明为什么不能只用 effective 参数数估算容量。若仅按 BF16 算，主 Embedding 约 1.25 GiB、PLE 打包表约 5.25 GiB，合起来已约 6.5 GiB；投影、归一化与视觉/音频参数还未计入。这里的“打包表”指把各层 PLE 放进同一张参数表，并非 4 bit 量化打包。真实装载预算仍要逐一统计所选 checkpoint 的张量与格式。

运行时还要给动态状态留地方。第 11 期的 BF16 原始 KV 净荷例子，在 128K 全局历史时，仅四个全局生产层已约 2 GiB，另有局部层状态；多请求同时保留历史时，这部分大体随请求数增加。加载期的权重副本、量化元数据、临时激活和注意力工作区也可能占用峰值，是否同时存在要看实际调度。因此，静态权重装得下，还不能推出整段推理装得下。

## 量化把权重字节缩到哪里

量化把较高精度的权重映射为少量离散值。常见分组形式可写成 `w≈s(q−z)`：`q` 是低比特整数，`s` 是一组权重共用的 scale，`z` 是可能使用的零点。所谓“4 bit 权重”，只说了 `q` 的宽度；存储还要容纳 scale、可能的零点、对齐，以及不适合量化的模块。

拿第 10 期的 gate 投影 `[2560,10240]` 做一笔**构造算术**。它有 26,214,400 个权重，BF16 净荷为 50 MiB。若每 64 个值用 4 bit 保存，并共用一个 BF16 scale，平均每值占 `0.5+2/64=0.53125` 字节，整张权重的理想净荷约 13.3 MiB。它比纯 4 bit 的每值 0.5 字节稍大，仍远小于 BF16；此处未计零点、分组索引和对齐，也不是 E4B 官方 Q4_0 的格式定义。

这一步直接改变第 10 期的存算比：单请求 Decode 对这张 gate 权重约做 52.4M FLOP。若只计从同一级存储读取一次权重，BF16 是约 `1` FLOP/byte，刚才的构造格式是约 `3.8` FLOP/byte。计算没有凭空减少，变化来自要搬的权重字节；这仍不是整层或整机的实测算术强度。

[Google Gemma 4 模型概览](https://ai.google.dev/gemma/docs/core)给出 E4B 不同格式的装载估算，可用来对照上述理想净荷：

| E4B 格式 | 官方装载内存估算 |
| --- | ---: |
| BF16 | 17.9 GB |
| SFP8 | 8.9 GB |
| Q4_0 | 4.5 GB |

官方表格含约 20% 的附加装载开销，仍不包含上下文带来的 KV Cache；工具和环境也会改变结果。它还列出使用 LiteRT-LM 的移动版 2.5 GB、纯文本移动版 2.2 GB。不同格式可能采用不同模块位宽，不能把“8B 参数 × 4 bit ≈ 4 GB”当作某个发布格式的文件大小或运行峰值。

## 芯片有没有用上压缩后的字节

对单请求 Decode，投影权重每步服务的输入行很少，权重读取难以摊薄。如果低比特权重在外存保持打包，搬到计算阵列附近才按块解包、取 scale，外存带宽需求才有机会下降。若运行时先把整张权重展开为 BF16 并长期放回外存，模型文件虽然小，每步读权重的带宽账却可能重新接近 BF16。量化收益发生在哪一级存储，取决于实际数据流。

![量化权重片上转为 INT8 计算与先展开 BF16 存回外存的两条数据流对比](assets/generated/quantization-dataflow-12-zh-v2.png)

*图：构造的 gate 权重例子。上路展示一种端侧整数执行路径：外存保持打包权重，片上解包为 INT8 计算值，激活量化为 INT8 后进入乘加，输出按 scale 重定标；下路若先展开 BF16 并存回外存，后续仍可能搬运 BF16 规模的权重。图中 50 MiB、13.3 MiB 和理想算术强度来自公式估算；具体 E4B 后端未必采用图中路径。*

在面向整数乘加的端侧实现里，压缩权重可在片上解包成 INT8 计算值。这一步主要是展开码值，**不必先把整张权重反量化成 BF16**。激活可以承接上一量化算子的 INT8 输出，也可以在进入矩阵乘前按自身 scale 量化到 INT8。随后做 INT8×INT8 乘加，以 INT32 等较宽位数保存累加结果。

若权重按组量化，不同组的部分和还要按各自 scale 重定标后合并，并处理激活 scale 与可能的零点。输出按下一算子的需要再量化为 INT8，或反量化到较高精度，例如交给需要较高精度的归约。量化与反量化沿算子边界安排，不等于每一步都生成一份完整的 BF16 权重。[LiteRT 的 INT8 算子规范](https://developers.google.com/edge/litert/conversion/tensorflow/quantization/quantization_spec)给出了这种整数输入、权重与宽位累加的一个公开例子。

这条整数路径还要有相配套的硬件：4 bit 解包、激活量化、INT8 乘加、宽位累加、按 scale 重定标，以及容纳权重块和中间结果的片上存储。任何一段供给不足都可能让阵列等待。另一类 `W4A16` 是 4 bit 权重配 16 bit 激活，可以在读取低比特权重后转换到较高精度进行乘加；[Google 同时提供这类格式与面向移动设备的 `wNa8o8` 格式](https://ai.google.dev/gemma/docs/core)。因此，不能把图中的 INT8 路径当作所有 E4B 发布格式的统一执行方式。Prefill 还能让一个权重块服务较多行，Decode 更依赖持续供给，实际收益仍要分阶段测。

PLE 与主 Embedding 的大表则按 ID 取行，主要先影响常驻容量，不会在每个 token 上顺序读取整张表。表项与 scale 的布局、单次读取粒度和缓存命中会决定查表带宽。KV Cache 又随历史长度增长：只量化权重，不会自动降低长上下文的 KV 读取量。权重、激活、累加结果和 KV 的位宽都要分别说明；从权重位宽无法推断其余数据的表示。

## 最后用四项结果决定格式

选定格式时，应同时记录**常驻容量、运行峰值、Prefill/Decode 速度和任务质量**。后训练量化（PTQ）是在训练后压缩模型；量化感知训练（QAT）在训练中模拟量化误差，让模型有机会适应低精度。[Google 已发布 Gemma 4 的 QAT 格式](https://ai.google.dev/gemma/docs/core)，包括 4 bit 权重格式和 E4B 混合位宽、优化 KV 的移动格式，但发布格式的存在不等于目标任务无需评测。

权重误差会经过多层计算传递，KV 量化还会改变后续每一步读取的历史数值。比较方案时要固定 checkpoint、量化方法、测试集、上下文、batch 与目标硬件，再看质量是否可接受，以及装载峰值、首 token 延迟、后续 token/s 是否符合要求。本章的参数算术和数据流分析没有替代这些测量。下一章转向另一类访存：Attention 的分数与概率中间表，能否不完整写回外存。
