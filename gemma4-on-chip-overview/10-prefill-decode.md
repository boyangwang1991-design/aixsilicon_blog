# Prefill 与 Decode：同一模型的两种计算形态

![Prefill 与 Decode 两种节奏的概念封面](assets/generated/cover-10-zh.png)

[系列索引](README.md) · 第 10 期

同样调用一套 Gemma 4 权重，用户发送提示词的那一刻与模型持续吐字时，计算形状并不一样。提示词已经全部给定，模型可以一次处理其中许多位置。这段叫 Prefill：线性层接收多行 `[S_prompt,D]`，同一权重服务多行，Attention 为后续生成准备所需的 K/V。首个回答 token 的等待时间通常包含这段工作。首个 token 选出后，模型才知道下一步要喂回哪个 ID；batch=1 的典型 Decode 步在线性层只有一行 `[1,D]`。一条回答的各个生成步因此有前后依赖。

两段工作共享权重，数据移动的代价却不同。Prefill 有较多 token 行可以复用权重；Decode 每步只有少量新行，却仍要使用权重并读取可见历史 K/V。这个差别会改变硬件的工作方式，也会改变我们该怎样衡量生成速度。

![Prefill 一次处理已知提示词，Decode 逐步生成并读取历史 KV](assets/generated/prefill-decode-hardware-zh.png)

*图：两阶段使用同一套权重。图中 `S` 是提示词位置数、`B=1`；每个 Decode 步读取当时可见的历史 K/V，具体读取量还取决于层类型和上下文长度。*

## 同一层在两阶段的矩阵形状

看 E4B 的一张 gate 投影矩阵，按数学约定是 `[2560,10240]`。Prompt 长 `S=128`、batch=1 时，Prefill 可写成 `[128,2560]×[2560,10240]→[128,10240]`；Decode 新增一个位置时是 `[1,2560]×[2560,10240]→[1,10240]`。两次都要用同一张权重，却分别为 128 行和 1 行产出结果。前者是大型矩阵乘，后者更接近矩阵向量乘，这解释了权重复用机会的差别。注意这里的数学矩阵方向与 PyTorch `Linear.weight` 的保存方向可能转置，算子语义一致。

Attention 的变化更明显。Prefill 局部层让 128 个查询分别看允许的前缀；因为 `128<512`，窗口尚未截断这段提示词。全局层也看完整因果前缀。Decode 到第 129 个位置时，只有一个新 Q，但要读取先前位置的 K/V；当序列超过 512，局部层的可见长度被窗口限制，全局层仍可能继续增长。E4B 有些层复用先前层的 K/V，并非每层各写一份缓存；产生 K/V 的层写入新位置，消费层读取可见历史。写入量与历史读取量应分开看。

## 从存算比看硬件该忙什么

存算比要先说清计量方向。这里用**算术强度**：每从某级存储搬运 1 字节数据，完成多少次浮点运算（FLOP/byte）；它越低，数据搬运越容易挡住计算。只看上面的 gate 投影，设输入有 `M` 行、权重为 `[K,N]`、每个权重占 `b` 字节。矩阵乘约做 `2MKN` 次浮点运算。如果每个权重从该级存储只读取一次，单计权重就需 `KNb` 字节，得到理想比值 `2M/b` FLOP/byte。以 BF16 权重的 `b=2` 为例，`M=128` 时是约 `128` FLOP/byte，`M=1` 时只有约 `1` FLOP/byte。同一张权重，在 Prefill 中服务 128 行，在单请求 Decode 中只服务 1 行，差别就来自这里。

![同一张 BF16 gate 权重在 Prefill 和单请求 Decode 中的理想算术强度对比](assets/generated/prefill-decode-arithmetic-intensity-zh.png)

*图：一次读取同一张权重，Prefill 让它服务 128 行，Decode 只服务 1 行，因此只计权重时的理想算术强度相差 128 倍。图中数据是公式估算，不是硬件测量结果。*

这个估算只数了一次权重读取，尚未计入激活、输出、K/V 和重复搬运，因此不是整层或整模型的实测算术强度。粗略判断硬件上限时，可以把可用算力 `P` 除以该级存储的有效带宽 `B`：算术强度低于 `P/B`，搬运数据通常会先限制吞吐；达到这个比值后，计算阵列才有机会吃满。Prefill 要让阵列持续有活干，需要把输入与权重分块放进片上存储，并让一个权重块尽量服务多行；Decode 单请求的权重计算量较少，权重和历史 K/V 的容量、带宽与读取效率往往更值得盯紧。把多个请求合成 batch 可以增加同一步的行数、摊薄权重读取，但也会增加并发 K/V 占用，并受请求时延目标约束。具体瓶颈仍要结合上下文长度、量化、缓存命中和设备测量判断。

## 为什么两个阶段不能只报一个速度

Prefill 处理已知提示词，通常由末尾 logits 选出首个回答 token；此后的常规自回归生成，要等前一枚 token 确定后才能开始下一步。如果只测后续 Decode 的平均速度，用户等首 token 的时间就消失了；若只报端到端 token/s，又可能掩盖稳定生成速率。首 token 延迟、后续 token/s 和整段耗时应分开记录，并给出输入长度、输出长度、batch 与设备条件。

测量首 token 延迟时，还要说明是否把模板、Tokenizer、设备传输和输出解码算进去。第二个 token 开始的 Decode 速率也应给出上下文长度，因为全局 K/V 的可见历史会随长度增长。一个 `tokens/s` 数字若没有这些条件，很难跨设备或跨模型比较。

可选的多 token 预测（MTP）会改变后续前向的安排，第 18 期结合 drafter 再谈。这里先留下一个关键问题：后续一步只输入一个新 token，前面那些 K/V 从哪里来？
