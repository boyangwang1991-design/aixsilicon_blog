# 14｜MPU 与 Firewall 怎样保护安全域？

[返回系列索引](../INDEX.md) · 中文初稿

一块安全相关存储器里的数据已经由 ECC 保护。如果另一个 master 通过合法总线事务，把错误但自洽的数据写进这块区域，ECC 会为新数据生成正确的校验位。读出时一切看似正常。防止这类越权写入，靠的是访问隔离，而不是存储位纠错。

## 拦截要发生在副作用之前

假设 CPU A 可以读写控制参数，DMA B 只能访问自己的缓冲区。MPU 或 firewall 在请求进入目标之前检查 master 身份、地址范围、读写属性和当前策略。合法请求继续；非法请求应被拒绝，并给请求方一个定义清楚的错误响应。更重要的是，目标寄存器或 SRAM 不能因被拒绝的事务发生任何副作用。验证中若只看见一个“拒绝”信号，却没有检查下游状态，隔离结论仍不完整。

访问策略本身也是状态。谁可以修改权限？更新多项规则时是否会出现短暂开放窗口？复位之后的默认策略是什么？若配置寄存器被破坏，检查器会变得更严还是更松？这些问题会影响所谓 freedom from interference 的实际论证。权限检查电路同时可服务 security 与 safety 目标，但两类目标的攻击/故障假设、响应要求未必相同，不能仅凭“有 MPU”就宣称干扰自由已经证明。

## 把案例收窄到一笔访问

沿着这个例子做故障实验：先让 CPU A 正常更新参数，再让 DMA B 向同一地址发起写入，检查拒绝响应、错误上报和目标内容是否保持不变。随后切换权限策略，在切换边缘重复两种请求。这样能同时看见越权写是否漏过，以及合法写是否被错误阻断。

读者最终应带走一个判断方法：访问控制的安全作用不在“拒绝了多少请求”，而在正确隔离了哪些主设备、地址和操作，以及策略失效时还能否保持所需边界。

**隔离器自己也有相反的失效模式。** ISO 26262-11:2018 对 MMU/访问控制类部件的示例同时考虑“本该允许却被阻断”和“本该阻断却被允许”。前者可能破坏安全功能的可用性，后者可能破坏隔离边界。测试只注入越权写入不足以评价整个安全作用；还要覆盖正常访问在配置更新、复位与错误恢复期间是否被意外饿死或延迟。若 DMA 也参与传输，其身份与权限不能默认等同于 CPU。

## 一次权限更新也可能造成干扰

很多访问控制 IP 允许软件更新地址窗口。若先撤掉旧规则、稍后才装上新规则，中间可能短暂“全拒绝”；若先装新规则再撤旧规则，也可能出现两个 master 同时可访问的重叠窗口。双缓冲配置加一次原子切换，是候选设计之一；另一种是更新期间暂停相关事务。选哪种，要同时考虑越权风险与安全功能是否能容忍暂时不可用。

安全分析还应覆盖 MPU 自身的相反失效：本该阻止的请求被放行，以及本该允许的安全访问被阻断或长期延迟。两者都可能影响安全目标，验证不应只测非法写入。
