# 26｜DFMEA、FTA、DFA 和 FMEDA 各在找什么？

[返回系列索引](../INDEX.md) · 中文初稿

一个 RAM Controller 的 ECC 解码器可能漏报，地址路由器可能选错 bank，Error Manager 也可能把真正的告警屏蔽。把这些条目放进一张 FMEDA 表之前，需要先弄清它们怎样影响上层功能、哪些组合能突破防护、哪些看似独立的路径共享同一根因。DFMEA、FTA、DFA 与 FMEDA 从不同方向检查同一架构；它们的价值是让遗漏暴露出来，而不是凑齐四个文件名。

## 用一条因果链贯穿四种分析

沿用第 25 章的教学要求：不可纠正的 SRAM 数据不得以正常有效数据供 CPU 使用。先把分析对象分层，例如 RAM Controller 包含地址路由、ECC 引擎、阵列接口和错误报告；ECC 引擎又含编码、解码、syndrome 与状态逻辑。这里的 component/part/subpart 是为了确定分析粒度和责任，不应机械规定每个 RTL module 都必须成为一行。失效原因可以是某个门级 stuck-at 或需求设计错误；失效模式可表述为“解码器漏报指定不可纠正码字”；局部影响是控制器把错误数据标为正常；上层影响取决于数据用途与其他诊断，不能未经传播分析就直接写“安全目标违反”。

**DFMEA**（设计失效模式与影响分析）沿部件向上问：这个设计部分以哪种方式失效，局部、上一级和系统层分别看见什么？它能发现“`UE` 被漏报”与“本该允许的访问被错误拒绝”是两个不同模式。应记录运行状态、是否有检测和缓解、谁承担响应，以及还有什么未分析。若表中写了“ECC 覆盖存储故障”，却没有限定数据位、地址译码、完整码字替换和解码器自身故障，就需要回到故障模型。DFMEA 是业界常用的设计分析名称；ISO 26262-9 规定的是相应安全分析目标与方法，并不强制所有项目使用同一个表格标题。

**FTA**（故障树分析）从相反方向出发，把“错误控制参数被正常使用并可能违反安全目标”定义为顶事件，再追问它需要哪些中间事件。一个简化树可能包含两支：错误数据已产生，且阻断/上报链失效；也可能有另一支是“写入时就把错误但自洽的数据重新编码”，此时读口 ECC 没有机会报警。AND/OR 门表达的是所选边界内的逻辑关系，不能把时间顺序、共同根因或条件事件全部隐藏进一个乘法概率。故障树的最小割集若出现“ECC 解码器漏报”，应能回到 DFMEA 的相应模式；若找不到，就有分析缺口。

**DFA**（依赖失效分析）检查上述两支能否被同一个原因同时触发或破坏。假设主 CPU、ECC、监控器都共用一条电源或复位，单一上游故障可能让错误产生、检测沉默、响应失效一起发生。此时不能把它们当作三个独立随机故障相乘。DFA 还覆盖级联失效，例如一个错误配置广播到两个本应独立的监控器。第 22 章用 Safety Island 展开了共享资源路径；本章把 DFA 放回分析闭环。[ISO 26262-9:2018](https://www.iso.org/standard/68391.html)将依赖失效分析与安全分析列为独立议题，[ISO 26262-11:2018](https://www.iso.org/standard/69604.html)补充半导体场景。

**FMEDA** 在定义好范围、失效模式、诊断与假设之后，加入随机硬件失效率、模式分布和诊断有效性，按安全目标分类单点、残余、多点与安全故障，并支持第 19、20 章所讲的 SPFM/LFM/PMHF 评价。它不能把一个设计阶段遗漏的需求按“极低随机失效率”消掉，也不能把注入次数直接转成 DC。DFMEA/FTA 找出新的逃逸路径后，FMEDA 的行和覆盖假设应随之修订；FMEDA 发现某种残余占比高，也会推动 TSC 加机制或缩小主张。

## 四份分析怎样互相校验

一个轻量的交叉检查办法是取一项顶事件，从 FTA 走到最小割集，再找每个基本事件在 DFMEA 的失效模式、DFA 的共因检查和 FMEDA 的分类/失效率位置。反向再从每个安全相关 DFMEA 模式走回至少一个顶事件或有理由的“不会违反安全目标”判定。若只有 FMEDA 行而没有系统影响，数值边界不清；若 FTA 只列 ECC 坏了，却没有 ECC 失效机制与验证，顶事件无法关闭；若 DFA 指出共享参考或时钟，独立性假设必须更新。

这些分析应在架构形成时启动，并随 RTL、物理实现、工艺、测试证据和集成条件迭代。所谓“设计完成后才做 DFMEA”的顺序会错过它最有价值的时机：在 IP 和系统接口尚可修改时发现盲区。正式工程篇需要目标设计的层级、故障模式分布和可公开的分析记录；本章不填造一个“已完成 FMEDA”的数字。
