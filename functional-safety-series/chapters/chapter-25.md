# 25｜一条 Safety Goal 怎样变成 TSC 和 IP 安全需求？

[返回系列索引](../INDEX.md) · 中文初稿

“SRAM 要加 ECC”看起来像一条清楚的芯片要求。但它没有说保护哪块存储、针对哪些故障、坏数据能否继续输出、错误由谁处理，以及处理必须赶上什么时间。把这句话直接交给 RTL，工程团队可以做出一个功能正确的 ECC，却仍无法回答它是否支撑上层安全目标。本章沿一条教学需求，把系统层的技术安全构想（TSC）分解到可实现、可验证的 IP 安全需求。

## SEooC 的起点是一组待核对的假设

如果芯片为已知 item 开发，车辆级危险分析、安全目标、运行场景与系统分配可以由相关团队明确提供。如果供应方开发的是 SEooC（Safety Element out of Context），就只能先定义预期用途和假设性上层安全需求：目标数据用途、允许的故障处理时间、外部时钟和电源、告警接收方、软件或外部硬件要完成的动作。它们是**集成时必须确认的假设**，不能写成“该芯片已经通过整车 HARA”。真正的车辆安全目标及 ASIL 仍要在 item 情境下确定；第 1、3 章已展开这条边界。[ISO 26262-11:2018](https://www.iso.org/standard/69604.html)为半导体和可复用 IP 提供相关应用指导。

拿教学例子说，假设系统不允许某类控制参数错误在使用后导致失控输出。上层功能安全需求可以要求识别错误并进入受控状态；技术安全需求则把工作分给存储控制器、错误管理器、处理软件和输出隔离逻辑。每一层都要回答“在什么状态、遇到什么故障、最迟何时产生什么可观察结果”，而不是把“使用 SECDED”复制到所有文件。

## TSC 同时包含技术需求与架构理由

技术安全概念 TSC（Technical Safety Concept）不是一张只标有 ECC、watchdog 和 Safety Island 的框图。它要把技术安全需求、系统架构及选择理由连起来：SRAM 控制器检出并阻止坏数据；Error Manager 锁存并升级严重事件；主 CPU 能处理时由软件执行恢复，CPU 不可用时由硬件路径隔离输出；共享时钟、复位和供电失效怎样影响这些路径。还要说明检测时间、传输时间与最终动作如何共同满足系统预算，哪些职责落在芯片外部。[ISO 26262-4:2018](https://www.iso.org/standard/68386.html)把技术安全需求、架构设计和 TSC 放在系统开发的相互迭代过程中。

一个可审查的 TSC 片段可以写成：在已初始化的安全相关 SRAM 发生指定不可纠正错误且被读取时，控制器不得交付正常有效数据；错误状态进入不依赖该笔失败事务的报告路径；如果软件路径无法在剩余预算内响应，独立硬件输出负责受控动作。这里的“被读取”暴露了一个重要问题：若数据长期不读，检测延迟可能无界。TSC 因此要决定是否加入巡检、启动测试或限制使用模式，而不能把这项缺口留给下游测试报告。

## IP FuSa LRS 把分配变成接口契约

团队可以把某个 IP 的功能需求和安全需求写进名为 **IP FuSa LRS** 的文件；LRS 是项目约定的文档名称，不是 ISO 26262 规定的统一文件名。对 SRAM 控制器，一条真正有用的安全需求至少写明：受保护地址范围和配置、码字及地址保护方式、错误类别、`data_valid` 与总线响应语义、错误锁存与清除、上报时限、复位/初始化顺序、测试模式限制和可验证判据。正常功能需求，如端口数与仲裁方式，也不能与安全需求矛盾。

例如把“检出不可纠正错误”拆成三项教学要求：读到目标故障模式时产生 `UE`；同一事务的正常 `valid` 不得成立；`UE` 必须在分配的时限内被 Error Manager 观察到。第一项可由 ECC 单元注入检查，第二项要跨控制器输出检查，第三项要在集成时检查报告路径。再加一项使用假设：集成者在首次安全相关读取前完成数据与 ECC 初始化。它不是 IP 内部已经完成的行为，应进入 Safety Manual，并在 SoC 启动验证中确认。

若可复用 IP 有多个数据宽度、ECC 选项、bank 数或时钟模式，需求与证据必须指向明确配置。某配置下的 syndrome 仿真通过，不能自动覆盖另一种地址映射或时序。架构修改也会反向改动 LRS：若 Error Manager 增加一级寄存器，原上报时限和故障容忍时间预算要重算；若 FMEDA 发现地址译码故障未覆盖，TSC 可能需要补地址保护。本章的箭头因此是追踪关系，实际工作需要反复迭代。
