# 27｜Safety Manual 怎样把 IP 的安全能力交给集成者？

[返回系列索引](../INDEX.md) · 中文初稿

供应方说 SRAM Controller 能检出不可纠正错误，集成方把 `UE` 输出接到普通可屏蔽中断。一次主 CPU 卡死后，告警虽在 IP 端产生，系统却没有任何实体在要求时间内执行隔离。这个失配不一定是 ECC 电路的错；它发生在 IP 能力与 SoC 使用方式之间。Safety Manual（安全手册）要让集成者看见这样的前提、接口和剩余责任。

## 先给每项安全主张画边界

可复用 IP 常按 SEooC 的使用假设开发。对于同一 SRAM Controller，必须注明受支持的参数组合、存储宏与物理位映射假设、地址是否参与 ECC、初始化顺序、错误注入模式、时钟与复位条件，以及哪种错误会被纠正、只检出或完全不在保护范围内。若写“支持 SECDED”，还需要补上保护的是哪个码字、不可纠正读的 `valid` 和返回码、状态锁存、清除顺序、Error Manager 的连接与最大报告时间。否则集成方可能正确连接信号，却错误理解它的语义。

一个安全手册条目应能被检查，而不只是写“建议启用 ECC”。例如：“安全相关读取前，集成者完成受保护 SRAM 全地址的数据与 ECC 初始化；启动流程检查初始化完成状态；在此之前阻止该区域被安全功能使用。”这同时告诉集成方要做什么、何时做、怎样留证据。对于 `UE`，应写清上层必须阻止坏数据消费、接收并锁存告警、在分配预算内采取动作；若该动作由系统软件承担，还需在 HSI 中定义中断优先级、屏蔽规则、重复事件和 CPU 不可用时的备用路径。

## AoU、推荐配置与剩余风险怎样写

AoU（Assumptions of Use，使用假设）是供应方分析成立的条件。它可能涉及供电工作范围、时钟精度、宏的物理交织、周期自检间隔、外部错误处理或诊断软件。推荐配置说明哪些参数组合已有分析与验证；未覆盖的配置不能靠一句“RTL 可参数化”自动继承结论。对于未覆盖的地址译码故障、完整合法码字替换、共同参考源或共享复位，还应明确残余风险与由谁补充机制，不能把它们藏在笼统免责声明里。

安全手册也要描述诊断机制自己坏了怎么办。LBIST/MBIST 未运行、ECC 报警线卡住、测试模式残留、watchdog 被无条件喂狗，都可能让集成后的诊断能力低于供应方假设。把“上电必须运行哪项测试、失败后禁止什么功能、正常运行中多久检查一次、告警怎样升级”写成可验证要求，才使集成责任可落实。[ISO 26262-11:2018](https://www.iso.org/standard/69604.html)把半导体/IP 的集成资料与安全应用说明作为专门问题；[ISO 26262-8:2018](https://www.iso.org/standard/68390.html)讨论分布式开发双方的接口和需求管理。

## 交接不能只靠一份 PDF

对按客户需求联合开发的芯片，双方还需约定谁定义安全要求、谁完成分析和确认活动、谁处理异常、谁保存哪份工作产品，以及量产和运行阶段的交接。分布式开发接口协议（DIA）解决职责与交付边界；Safety Manual 说明产品怎样安全集成，两者作用不同。即使供应方完成了自身的安全分析，集成者仍要逐条验证 AoU 是否在目标 SoC、软件和车辆运行情境中成立。

一张实用的集成核对表可以只选三项：`UE` 是否接到预期错误管理通路、首次安全读取前初始化是否确实完成、主 CPU 不可用时能否在时间预算内进入受控状态。每项都应有配置版本、测试方法和结果；如果某项不成立，要修改架构、补机制或收窄安全主张。不能只在核对表上写“符合手册”而不记录实际连接与时序。

最后还要防止文件版本错配。IP RTL、宏配置、Safety Manual、FMEDA、故障注入报告和 SoC 连接图应能对应同一基线。一个 ECC 选项变更或中断路径加一级寄存器，可能改变检测时间、故障覆盖和 AoU；第 28 章会继续讨论这些证据怎样组成可评估的安全论证。
