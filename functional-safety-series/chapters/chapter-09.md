# 09｜Watchdog 怎样发现“CPU 还在运行却已失控”？

[返回系列索引](../INDEX.md) · 中文初稿

一个最简单的 watchdog 会在计数器到期前等待 CPU 写入一次服务值。CPU 没来，watchdog 报警。可如果 CPU 跑飞后仍能周期性执行“喂狗”代码，计数器就会被不断重置，看起来一切正常。问题因此从“CPU 是否活着”变为“CPU 是否按约定推进了关键工作”。

## 从超时到窗口

普通超时机制主要发现没有按时服务的情况。Window watchdog 再增加一个“太早也不合法”的约束：启动后的封闭区间不接受服务，开放区间才允许服务，到期仍未服务则报错。这可以识别某些异常快循环或无条件频繁喂狗，但窗口如何配置必须考虑任务抖动、中断、总线延迟和启动过程。窗口过窄会误报，过宽则延长发现问题的时间。实际产品的窗口规则可能不同，正文应以采用的实现为准；例如 [AMD 的窗口 watchdog 文档](https://docs.amd.com/r/en-US/am026-versal-ai-edge-prime-gen2-trm/Window-Watchdog-Timer-Mode)区分封闭与开放窗口，并描述过早服务事件。

更强的方案会让软件在完成若干关键检查后才发 heartbeat，或要求对一个变化的 challenge 给出正确响应。它们提高了“机械喂狗”的门槛，也把正确性要求引入软件和通信路径。无论机制多复杂，若 watchdog 与 CPU 共用已经失效的时钟，它可能一起停止；独立时钟与自身诊断便成为设计问题。

## 报警之后怎么办

Watchdog 输出可以进入 Error Manager、触发中断、复位或系统降级。选择取决于系统要求：复位能否恢复功能？复位期间输出是否受控？若软件已失控，依赖它执行恢复是否合理？这些问题说明 watchdog 是一条诊断路径的起点，不是完整的安全策略。

一个能检验喂狗协议的场景是：采样任务完成了、控制计算没有完成，但周期性定时中断仍在执行。如果定时中断无条件写服务寄存器，watchdog 会持续被喂饱；如果只有控制计算提交了本轮结果才允许服务，下一次超时就能暴露这类进度停滞。但这仍不能发现“计算按时完成、结果却错了”，那是 lockstep、结果合理性检查或其他机制的问题。设计应明确 heartbeat 证明了哪些任务阶段，不能把“CPU 仍有指令执行”写成“安全功能正常”。

**机制强弱不能只看名字。** ISO 26262-5:2018 的诊断覆盖附录将有独立时间基准的普通 watchdog、带时间窗口的 watchdog，以及时间与程序顺序结合的监控区分讨论。那是分析起点，不是对某颗 IP 自动适用的覆盖率认证。真正评价时仍要知道喂狗软件是否被关键任务约束、窗口是否容忍正常抖动，以及计数器或时钟故障如何发现。一个“窗口狗”若始终由空循环按时服务，也可能错过真正的问题。

## 喂狗协议应依赖实际进度

一种软件约束是：采样、检查、计算和输出提交都完成后，才更新本轮 heartbeat；watchdog 根据阶段或序号判断进度。这样无条件循环喂狗更难伪装“关键工作已完成”。但若所有阶段都由同一个错误状态机自报完成，它仍可能自证正确。Challenge-response 增加动态性，也增加挑战生成、响应计算与通信路径的失效分析。

窗口应与最坏任务时间匹配。调宽窗口可减少误报，也会增加发现故障的时延。写具体 IP 时，应把配置、时钟源和故障反应时间放在同一张时序图里。
