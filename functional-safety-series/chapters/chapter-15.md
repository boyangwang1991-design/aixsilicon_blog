# 15｜错误中断发不出来时怎么办？

[返回系列索引](../INDEX.md) · 中文初稿

ECC 检出不可纠正错误后，错误并没有自动变成系统动作。事件可能先被锁存，送到 Error Manager，经过优先级和屏蔽规则，再由 IRQ 或 NMI 通知 CPU，最后由软件读取状态并执行处理。链上任何一环失效，源端“检测成功”与最终“系统已响应”就会分开。

## 从错误源走到处理程序

用一次 SRAM 读错误看这条链。源端应保存足够状态，让短脉冲不因下游忙碌而消失。Error Manager 需要知道该错误是否可恢复、是否允许屏蔽、是否应升级。中断控制器负责把通知送达 CPU，软件在读取状态后，才知道是哪个地址、哪种错误以及是否仍能继续。若软件先清除告警再读取详情，可能丢失诊断信息；若事件在清除期间重新到来，又要定义是否会被重新锁存。

普通 IRQ 可能被更高优先级任务长期推迟，也可能被软件屏蔽。专用安全 IRQ、NMI、冗余错误线或超时升级是不同的设计选择，并没有一种对所有系统都合适。NMI 能减少某些屏蔽问题，却不能解决 CPU 本身已经停止执行、时钟丢失或软件处理程序错误。严重故障是否直接触发硬件动作，要由系统故障处理要求决定。

把时序摊开会更容易发现漏洞：不可纠正错误在 `t0` 被 ECC 检出；错误源锁存事件，同时阻止这次读数以正常 `valid` 交付；Error Manager 在 `t1` 接收；CPU 在 `t2` 进入处理程序；系统在 `t3` 完成受控动作。如果普通 IRQ 在 `t1` 之后被屏蔽，设计就要回答谁在到期前发现“事件仍未处理”，以及替代路径是否还能工作。只测 `irq=1`，无法证明 `t3` 赶得上危险输出。

## 验证整条报错路径

有解释力的测试不只注入 ECC 错误，还要观察源端锁存、Error Manager 状态、中断到达、软件读状态和最终动作。再故意屏蔽普通 IRQ 或让 CPU 忙碌，看预定的升级路径是否生效。若系统没有升级路径，就应如实写明响应依赖条件。PLIC、SIC、GIC 等控制器的行为并不相同，文章使用哪种架构，就应以该架构的实际语义和接口为准。

错误源越来越多时，统一记录、分类和升级通常由 Error Manager 承担。它自身的事件丢失、配置错误和共因依赖也要进入故障分析；否则集中管理会把多个来源的风险汇到同一个薄弱环节。

**中断控制器也要进故障分析。** ISO 26262-11:2018 的数字部件失效模式示例包含中断缺失、意外中断、过早/过晚以及携带错误信息。于是验证不仅要故意“丢掉中断”，也要看误报如何处理、错误源标识会否串线，以及延迟是否超过故障反应预算。专用安全 IRQ 若与普通 IRQ 共用相同路由瓶颈，名字上的“专用”未必带来实际独立性。

## 丢失、误报和迟到是不同故障

中断路径可能出现四类结果：应发未发、无事件却发、送达太晚、带错源标识。若只把所有故障注入都设计成“拉低 IRQ”，其余情形不会被检查。事件锁存和软件读取顺序又会带来竞态：软件清除旧事件的同一周期，新事件是否保留？严重事件是否可被普通掩码屏蔽？错误源编码损坏会不会让处理程序采取错误动作？

因此，端到端测试应为每类失效定义观察点和响应时间。系统可选择 NMI、专用线或硬件直达动作，但无论哪种路径，都要检查它是否与普通中断共享同一失效根因。
