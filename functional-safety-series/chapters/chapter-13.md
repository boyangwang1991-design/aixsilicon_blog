# 13｜E2E Protection 怎样发现数据送错、送迟或重复？

[返回系列索引](../INDEX.md) · 中文初稿

一份控制命令从生产者走到消费者，沿途可能经过软件队列、DMA、片上互连、共享存储器，甚至另一颗 ECU。链路每一跳都符合协议，消费者拿到的仍可能是旧命令、别的信号的命令，或被修改过的命令。E2E Protection（端到端通信保护）的出发点，是让**生产者与最终消费者**共同检查同一份数据的身份、内容和新鲜度，而不只依靠某一个中间接口的局部校验。

## 保护字段各自回答什么

一个教学用消息可以包含 payload、Data ID、序号或 alive counter，以及 CRC。CRC 按双方约定的字段、位序、初值和多项式计算，用于发现其能力范围内的偶发内容损坏；Data ID 把校验绑定到预期数据类型或通道，帮助识别误路由和混淆；计数器让接收者检查重复、丢失和乱序；独立的接收超时监控处理长时间没有新消息的情况。[AUTOSAR 的 E2E Library 规范](https://www.autosar.org/fileadmin/standards/R4.3.1/CP/AUTOSAR_SWS_E2ELibrary.pdf)给出了 Profile 1 的 CRC、Data ID、计数器与超时语义示例。这里借用其机制解释问题，不把某个 Profile 直接规定为芯片内部通道的唯一实现。

例如消费者上次接受序号 7，下一帧也报 7，但 payload 不同。只验证 CRC，可能认为新帧内容自洽；检查计数器才会发现重复或状态不一致。若另一个通道的完整帧被误送过来，CRC 也可能仍正确，Data ID 才提供预期来源或数据类型的约束。若上游在**生成 CRC 之前**就把数值算错，后续保护字段会忠实保护这个错误数值；E2E 不能替代源端计算的独立检查。

## 芯片内链路的保护边界要画清

对于 SoC 内部，E2E 可以是从传感数据生产 IP 到使用它的安全处理单元，也可以是从 CPU 软件写入命令到执行 IP 最终采纳命令。保护信息必须在需要覆盖的路径**之前**生成，并在最终使用数据**之前**检查。如果每过一个桥接器就重新计算 CRC，上游已经损坏的数据可能被包装成新的合法消息；如果只保护 AXI 一段，却在 DMA 缓冲区或软件复制后才使用，也不能声称全路径受保护。E2E 的“端”由安全要求和故障路径定义，不等同于固定的总线接口边界。

芯片内实现还要回答哪些字段纳入 CRC，地址、目标 IP、命令类型和长度是否需绑定，计数器位宽与回绕如何处理，允许连续丢几帧，复位后的第一帧怎样同步，以及接收端何时拒绝数据。CRC 不保证发现所有多位错误，计数器也不保证识别任意长度的重放；诊断能力应按选用的 Profile、消息长度和故障模型核对。对于恶意篡改，普通 CRC 和计数器不是认证机制，安全威胁模型需要另行设计。

## 从检出走到动作

验证至少可注入 payload 位翻转、整帧重复、跳号、乱序、误路由、延迟和完全丢失，分别检查消费者的 CRC、Data ID、计数器和超时判定。还要在保护码生成前、传输途中、检查通过后各选一个注入点，明确哪些故障本来就不在保护边界内。检查结果不能停在 `e2e_error`：消费者是否拒绝旧值、保留上次可信值或进入受控状态，以及这个动作能否在时间预算内完成，都属于安全相关接口契约。

这里的**通信内容端到端保护**与第 2 章“故障发生到受控动作的端到端时间”分别回答数据是否可信和响应是否及时。评价实际实现时，还需拿到消息字段布局、允许丢帧策略、独立检查器和故障注入结果。AUTOSAR 的机制定义或 AXI VIP 的协议通过记录，不能直接当作某颗 SoC 已具备 E2E 保护的证据。
