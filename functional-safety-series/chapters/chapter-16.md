# 16｜Error Manager 如何避免成为单点故障？

[返回系列索引](../INDEX.md) · 中文初稿

当 ECC、watchdog、clock monitor 和总线监控器都能报错时，CPU 不可能只靠读取几百根独立信号决定动作。Error Manager 的任务，是把分散事件转成可记录、可分类、可升级的系统信息。它的价值在于统一语义，而不只是把信号做一次 OR。

## 一次多源错误怎样处理

设想 SRAM 的不可纠正错误与总线超时在相邻周期到达。简单 OR 只能说“有错”；系统可能还需要知道先发生什么、是否来自同一事务、哪个错误决定响应等级。事件锁存可以保存短脉冲，计数器帮助观察重复出现的错误，分类与优先级规则决定通知途径。但掩码尤其危险：调试时允许屏蔽的事件，量产配置是否还可屏蔽？配置权限和状态读取都应被清楚定义。

输出也不该只剩一根“总错误”。有些错误可由软件处理，有些需要硬件快速隔离或复位，有些需要保留运行以完成受控降级。Error Manager 负责执行预先定义的策略；它不能凭自身判断发明安全目标。策略表必须与系统要求、故障处理时间和软件行为对上。

## 谁检查管理器本身

集中化带来新的单点风险：事件输入卡住、内部分类位损坏、掩码意外打开、输出线路断开，都可能让多个安全机制的报告同时失效。设计上可以考虑上电自检、周期性测试、关键错误直通路径、配置保护或独立监控，但每项都会增加面积、时序与验证工作。是否需要它们，取决于系统故障分析，而非一个通用模板。

审查这类 IP 时，可以反过来注入管理器自身的故障：把某个输入固定为无事件、翻转关键分类位或阻断一条输出，观察自检或独立路径是否发现。若最严重的事件也可能被它静默丢掉，就要重新检查系统是否把所有响应都押在同一条通道上。

**潜伏故障尤其要防。** 如果 Error Manager 的一条输入线断了，而平时从未有错误到来，系统可能长时间不知道它已经失去诊断能力。等另一个故障真的发生，双重失效才显现。ISO 26262-5:2018 对相关潜伏故障的检测区间与证据提出单独要求，这也是为何管理器自检不能简单排到“有空再测”。自检周期、覆盖的线路以及自检期间的正常报错行为都要写成要求并验证。

## 一张小策略表比“统一管理”更有用

假设三个输入分别是可纠正 ECC、不可纠正 ECC 和主时钟丢失。前者可能只需计数与软件通知；第二种需要阻止坏数据消费并按系统策略升级；第三种若使 CPU 无法工作，就不能只等待普通 IRQ 处理。策略表至少要写输入是否锁存、是否允许屏蔽、优先级、输出通路及清除条件。两个事件同时来时，较低优先级事件也不应无声丢失。

这张表不是通用安全策略；它是审阅工具。若设计把“不可纠正”事件的掩码位做成复位后默认开启，或者自检会暂时关掉所有输入，就应在表里立刻显露。

## 配置与测试模式怎样让诊断悄悄失效

看一条比“报警线断了”更隐蔽的链：调试软件曾打开 ECC 错误注入并临时屏蔽相应告警，随后系统复位；如果测试模式位被错误保留，或者 Error Manager 的掩码寄存器在复位后恢复为屏蔽状态，下一次真实的不可纠正错误可能被源端发现，却到不了最终动作。此时 ECC 单元测试和普通功能回归都可能通过，失效发生在配置、生命周期模式和事件路由的交界处。

设计时要为每个安全相关配置位回答四件事：谁能写、什么时候能写、复位/低功耗恢复后是什么值、写错或读错后谁会发现。写保护、关键位冗余或编码、寄存器 readback/CRC、锁定后拒绝修改，都可以作为候选措施；但 readback 若与原配置经过同一条失效的数据路径，不能自动当作独立检查。量产模式是否允许进入 DFT/debug，进入时如何禁止安全相关输出，退出后是否必须重新初始化和测试，也应进入状态机，而不是只写在调试手册里。

一组有价值的验证场景是：在正常运行中翻转关键掩码位，检查配置诊断能否在允许的潜伏故障检测间隔内报警；在测试模式切换边缘同时注入真实错误，检查事件是否丢失；复位和低功耗唤醒后读回配置，再检查第一笔安全事务之前是否已恢复保护。若调试端口可修改 Error Manager、MPU 或 watchdog，多条安全机制可能被同一模式控制信号同时关闭，还要放进第 22 章的依赖失效分析。相关思路可在 [ISO 26262-11:2018](https://www.iso.org/standard/69604.html)对共享测试/调试逻辑及配置保护的讨论中找到半导体语境。
