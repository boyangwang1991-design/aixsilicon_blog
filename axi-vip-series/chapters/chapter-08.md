# AI 辅助芯片验证，怎样让 AXI VIP 越用越可靠？

[系列目录](../README.md)｜简体中文，英文版待补

下一次让 AI 为一个新 IP 搭建验证环境，最有价值的输入是什么？除了 VIP 源码，还有一份明确的能力范围、一个能运行的接入方式，以及前次问题留下的检查。缺少这些约定，AI 仍会重新猜默认值、响应含义和完成条件。

前面七章已经解释了 AXI 协议、现有架构、独立预期、冻结结果和桥接实战。本章把它们收束为可复用的研发过程：项目怎样消费组件，使用经验怎样返回组件，以及其他 VIP 的教训怎样改变下一轮工作。

## 交给新项目的输入，应当足够具体

新项目首先需要知道接口角色和协议子集。是用主动 master 验证 AXI slave，还是用主动 slave 响应 AXI master？使用 Full 还是 Lite？ID、地址和数据位宽是多少？支持哪些 burst、多少笔在途、什么复位行为？这些答案决定环境结构，不能由 AI 根据模块名猜测。

随后给出组件版本、工具基线和最小构建入口。以本系列为例，当前证据对应 1.0.0、VCS W-2024.09-SP1、UVM 1.2；Lite 主动 master 当前一笔在途。若项目提出其他条件，需要增加对应验证，不能仅因为类能够参数化就宣称已有结果覆盖了它。

最后提供产品契约：地址空间、访问转换、错误映射、副作用和完成语义。对于 AXI-to-APB 桥，这些信息帮助 AI 生成产品模型和 scoreboard；公共 VIP 继续负责驱动、观察及协议检查。复用的结果，是产品层需要新写的东西变得清楚。

## 公共组件和项目环境各自保留自己的答案

把所有项目行为塞回 VIP，会让它逐渐依赖某个 DUT。反过来，每个项目复制一套总线驱动，则会重复承担相同缺陷。实用的分界是：与具体产品无关、能够以协议或组件接口解释的行为，适合留在公共层；寄存器语义、地址映射和特有策略，留在项目层。

| 产物 | 公共 VIP 保存 | 消费方保存 |
| --- | --- | --- |
| 行为模型 | 握手、响应关联、内存 lane、复位处理 | 地址转换、寄存器副作用、产品策略 |
| 测试 | 协议正反例、参数与配置、基础 API | 产品功能场景、实际接入回归 |
| 使用约定 | 角色、类型、默认值、版本与能力范围 | 实例层次、连线、复位 owner、项目参数 |
| 新发现 | 可复现的公共缺陷与修正 | 集成差异或产品行为修正 |

在工程上，一个问题也可能跨两层。例如 VIP 修正了等待响应的结束行为，消费方的超时用例就需要确认是否仍按照预期处理失败。归属明确不意味着只跑一边的测试。

## 让 AI 从其他 VIP 的经验中改进工作方法

APB 和 AXI 的协议复杂度不同，但很多研发教训可以迁移。APB 对等待期间稳定性的检查，提醒 AXI 分别检查五通道 stall；被动观察不应改变模型状态的要求，也适用于 AXI；复位必须有清楚 owner 的经验，可以减少多组件同时驱动复位的混乱。

迁移时要保留机制差异。APB 一次访问的完成条件不能直接替代 AXI 的多通道关联；APB 序列的串行结构，也不能证明 AXI 多笔在途时按 ID 回填正确。AI 应当提取“要检查什么”的经验，再根据新协议重新设计检查。

AXI 的发现同样可以反向帮助其他组件。构造函数默认值需要脱离随机化单测，适用于很多 UVM 配置对象；响应必须先检查存在，适用于所有有异步完成通知的 VIP；独立字节向量可以用于总线桥、DMA、存储模型及其他数据搬运逻辑。

这些经验如果只写成“注意默认值”“注意并发”，仍然太模糊。更有用的输入是失败条件和验收条件：直接构造配置对象后应有什么值；发出八笔唯一 ID 写之后应有八个独立完成结果；哪个线程不能被临时等待分支清理。

## 一次新需求怎样进入公共版本

假设新项目希望提高某种配置的在途能力。先确认这是协议能力、现有实现边界还是产品需求，再确定需要改变哪些队列、资源限制和完成行为。这个例子是研发方法，不表示当前已经执行了该扩展。

AI 可以据此提出影响分析、修改候选与定向测试。审阅时应优先看旧约定是否保持：同 ID 顺序、跨 ID 关联、最大容量附近的停止和恢复、背压、复位以及不相关实例的隔离。新场景通过之后，还要运行受影响的公共回归，并回到消费方确认。

若只有构建配置或使用方式改变，就更新接入样例及检查；若公共行为改变，就更新版本说明和证据身份。不能拿旧版的覆盖数字为新版修改背书。源代码、配置、运行条件与结果应能够一同定位到具体批次。

## 留下可执行的经验，而不只是一次总结

下一轮 AI 研发的上下文可以组织为一份简短任务书：当前版本与已验证条件，项目的接口和产品契约，本次新增目标，独立预期的来源，以及必须通过的定向与回归检查。任务完成后，再把真实差异写回这些材料。

例如，本系列的 READY 经验最终应落实为构造后检查；B 响应经验落实为数量、ID 和对象完成断言；字节 lane 经验落实为固定预期向量；桥接经验落实为两侧观察和产品转换检查。它们每次执行都可能发现回归，价值比一段无人再次核对的调试心得更稳定。

这套 AXI VIP 已有具体实现、冻结自验证结果和历史 IP 接入记录。持续使用它时，新的项目需求提供新的观察角度，公共回归把有价值的发现留住，AI 再依据这些更清楚的输入参与研发。组件与方法就这样一起积累，后续 IP 的验证也有了更可靠的起点。
