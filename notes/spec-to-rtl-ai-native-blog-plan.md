# 《从 Spec 到 RTL：我正在尝试一种 AI-Native IP 研发流程》文章规划

规划日期：2026-09-27。内部编辑资料，不是公开正文或发布材料。本轮只读核对 reference 快照、研发 Skill 文本、工程实现及已有文章，没有重跑 EDA，也没有执行参考仓的 Skill。来源快照及 SHA-256 见同目录 `spec-to-rtl-ai-native-sources.json`。

## 文章定位与核心判断

保留用户标题。“我正在尝试”与目前材料相符：已经有多个项目的具体实践，也有不断修订的方法。建议写成有案例支撑的方法文章，回答：**怎样把 AI 的工作组织成一段可以继续推进、检查和复用的 IP 研发过程？**

文章中心句：我正在把需求、设计决定、实现、验证和反馈组织成 AI 能持续参与的工程过程，让每次修改有明确输入、可执行检查和可继承的结果。

文中的 AI-Native 是作者对自身工作方式的定义：AI 从需求澄清开始参与；工程状态保存在可读文档、代码与运行记录中；工具检验结果；项目经验经过筛选进入下一次任务使用的规则和资产。不把这个词当作已形成共识的行业标准。

读者应带走三件事：怎样写出可检查的 Spec；怎样划分人、AI 与确定性工具的职责；怎样让一次修正沉淀为规则、测试或资产。正文建议约 4000–5000 中文字，英文完整对应，长度按解释需要调整。

## 推荐叙事与章节

### 开头：一个 lock 位，为什么还不算“锁住了”？（约 350 字）

用 AXI MPU 的实际评审发现起笔：需求要求配置锁定后禁止改写，早期 RDL 没有表达对配置寄存器写入的抑制。修正增加写使能控制、重新生成 CSR，再用定向用例检查锁后改写。

随后提出全文问题：一句自然语言怎样落实为一组互相对应的行为、结构与检查？这样读者先看到研发对象，再理解 AI-Native 的含义。

可用开头草案：

> “配置锁定后，软件不能再修改权限。”这句话看起来已经足够明确。可在一轮 AXI MPU 评审中，寄存器描述仍漏掉了对配置写入的抑制。补上一个 lock 字段，还需要把它接到真正控制写入的位置，并用锁定后的改写操作检查结果。
>
> 这个细节很适合解释我正在尝试的研发流程：AI 从需求整理开始工作，继续参与架构、实现和验证；每走一步，都要把上一步的意思变成可以检查的工程对象。

这段是根据记录组织的表达，不补写用户当时的对话、心理或具体操作时间线。

### 1. Spec 要写到什么程度，AI 才有明确的工作边界？（约 650 字）

以“锁定后禁止改写”为例，把问题拆成保护对象、允许的写入、锁本身的变化规则、复位恢复与检查方法。解释 Spec 会逐层细化，需求阶段不必把 RTL 全部设计完。

用四个自然问题介绍四份设计材料：

- LRS：外部应观察到什么行为，怎样验收？
- HLD：采用什么架构和保护机制，为什么？
- LLD：字段、写使能、优先关系、复位与时序怎样实现？
- VPLAN：用什么激励、观察点和预期判断要求满足？

配一张紧凑的“同一条需求如何逐层细化”表，不复制原仓长编号或目录树。表中的架构归纳要标明是本文教学整理，不能冒充历史设计的原始逐阶段记录。

### 2. 把设计意图留在工程里，让工具维护派生视图（约 700 字）

解释当前 IP Skill 的精确分工：Markdown 正文与 META 保存设计意图；extractor 抽取 YAML/JSON 供检查和下游使用；寄存器结构由 SystemRDL 定义，生成 CSR RTL、头文件等视图。改变源文件后重新抽取、生成与检查。

重点讲“一处修改为何会影响几类产物”。锁的行为约定、RDL 写使能属性、顶层 RTL 控制、验证预期各自承担什么责任。

要避免两种误读：Markdown 经抽取就能确定性编译出所有任意 RTL；所有仓库都使用同一种事实源。本文描述的是当前 IP Suite 的设计组织，CBB、HWIF、SoC 的数据归属另有合同。

### 3. Skills、工具和资产仓，各自让 AI 多做哪一部分工作？（约 800 字）

在读者已经理解需求链以后再介绍工作系统：

- 人确定目标、约束、取舍与验收范围，并审视规则本身。
- AI 按 Skill 整理设计、提出候选、修改 RTL/测试、阅读工具反馈并修正。
- Skill 保存步骤、输入输出、领域检查方法与已有经验；规则存在不等于已执行通过。
- 确定性工具负责抽取、生成、构建和检查；lint、仿真、综合回答不同问题。
- 资产仓保存可复用的实现、验证组件、模型及其配置/版本边界。

介绍 CBB（基础逻辑构件）、IP（完整功能与接口责任）、VIP（验证组件）的分工；ESL 是按需采用的架构探索分支。

参数化和 Generator 用一小段交代：行为叶子模块仍用 SystemVerilog，结构拼装可以交给 Python Hardware IR/Graph；配置合法、能够生成和已在该配置验证通过是不同状态。不要把现有参数扫描写成 AI 已自动发现全局最优架构。

### 4. AI 写出的实现和测试，怎样避免一起“自洽地出错”？（约 900 字）

使用 AXI4 VIP 的具体记录：读写路径地址映射存在相同错误，回环仍通过；基础语义测试用明确预期把问题暴露出来。同轮还发现测试期望自身的错误，因此测试失败也要核查 oracle。

解释独立预期的来源：协议定义、人工核对向量、可审查的不同推导方式。把同一个公式搬进第二个文件，不能证明独立性。

再讲负向检查：必须确认违规已发生在目标接口和时序窗口，才能评价 Checker 是否检出。无需罗列全部覆盖率。

如使用数字，只引用 2026-09-02 的 79/79 基础测试，紧邻注明 VCS W-2024.09-SP1、UVM 1.2、seed=1，以及它是该批基础测试的范围；不将不同时期结果相加。正文也可完全不写通过数，以错误机制和修正为重点。

### 5. 每次修改，要留下什么给下一次研发？（约 700 字）

从修正回到方法与资产：针对具体错误补测试，修复公共组件，经过判断后将通用经验写入 Skill。

AXI4 VIP 日志明确记录基础 Unit Test 机制同步进入 Skill、模板和项目工程，也记录需求与架构经验回写。描述同轮建立和修订的过程，不虚构“某个 bug 单独导致了全部规则”的严格因果顺序。

说明证据关联到配置、源码、工具与执行批次；文件哈希帮助确认版本归属，不能证明设计正确，也不能证明评审者身份。现行 IP Skill 对源内容变化采用保守失效规则，不宣称已实现精准、最小化的增量重跑。

需要 PPA 时，让综合结果进入取舍，但本篇不必新增性能数字。若引用结果，保留库、角、约束、工具和综合估计边界。

### 结尾：我希望下一款 IP 从哪里开始？（约 300 字）

落在可观察的积累：下一次开始时，手里已有更清晰的需求模板、验证过的构件、能抓住旧错误的测试以及修订过的方法。可接一句 SoC 集成需要配置、接口与依赖信息，使“交付 RTL”有明确消费者。

下一步写成作者方向：继续在更多 IP 上验证这些方法的适用范围、改善跨资产复用与变更后的检查。没有工时对照就不宣称倍数提效，不将整套流程描述为无人值守完成芯片研发。

## 已核对事实与写作风险

1. 当前 IP 主 Skill 已明确 Markdown 设计源、canonical 派生模型及 SystemRDL 结构源。其顶层 README 保留过时的数量与 SSOT 说法，应以具体 Skill 当前合同为理解依据，不把 README 当作全部最新细节。
2. AXI MPU FIND.AXI_MPU.004 记录写保护遗漏及修正；当前 RDL、顶层 RTL 和 `tc_config_lock.sv` 中存在相应实现/检查。历史报告记录回归通过，本轮没有重跑，也没有重新绑定所有历史原始日志。
3. 重要编辑边界：当前 `cfg_swwe` 为标量，任意 region lock 会抑制全部 region 配置写。不能将此案例宣传成逐区域独立锁定已经验证。现有测试先锁 Region0 后置全局锁，也不能单独证明未预锁情况下全局锁路径的全部行为。正文围绕“写保护需要真实写使能与检查”展开；若要扩大到完整锁语义，应另行核对/补测，不能用已记录 PASS 消除此问题。
4. VIP 2026-09-02 日志明确写出读写对称错误、79 个 golden cases、测试自身错误及 Skill 更新；可支撑该反例。不能据此认为 MPU 已接入这套 VIP，现有博客也把该接入图限定为方案示意。
5. 当前 Skill 是方法快照，历史工程可能使用不同版本和目录。文章要区分“现在采用的规则”与“当时记录的执行结果”，不能宣称所有历史项目都已满足最新全部门禁。
6. 已检查嵌套 PQC 发布包，含 `ai-pqc-rtl.md` 和 `ai-pqc-rtl.html`；本轮只读条目和哈希，不提取、不导入正文。已有 PQC 文章可作补充阅读，无须重复迁移。
7. 已概览七组 reference 的相关材料，但未穷尽全部 RTL/日志。素材足以规划方法文章；完整安全/性能/全流程签核、具体 AI 模型归因和人类耗时比较不在本轮证据范围。
