# 《为什么 AI 写 RTL 容易，做一个真正可交付的 IP 很难？》文章规划

日期：2026-09-27。内部编辑资料，非公开正文。本轮只读核对已有博客、SPI2APB 工程报告与集成说明、WDT 集成说明及 IP Skill 的参数验证/发布合同；未运行参考工程，未重跑仿真或综合。来源与 SHA-256 另存 `rtl-to-deliverable-ip-sources.json`。

## 定位：从接收方的角度解释交付

建议保留用户标题，但开头尽早限定“容易”的含义：AI 降低了获得 RTL 初稿、常见结构和候选实现的门槛；复杂且满足约束的 RTL 设计本身仍有难度。不能把标题扩写为“AI 已经能轻松写对任何电路”，也不做没有实测依据的速度比较。

本文要回答：**当另一个工程师把这款 IP 接入自己的系统时，哪些原先藏在开发环境里的假设，会变成必须说明和验证的责任？**

中心判断：RTL 描述一个实现；交付还要让接收方知道它在什么配置、时序、复位和异常条件下成立，有哪些检查依据，改变条件后需要重新确认什么。

“可交付”按双方约定的范围定义。内部评估包、供系统集成使用的版本、完成特定签核的发布版本，承诺不同。本文聚焦有明确使用范围、可执行检查入口和已知边界的工程交接，不把所有 IP 都要求为独立完成流片签核的商业产品。

与上一篇的关系：上一篇《从 Spec 到 RTL》讲工作如何组织，本篇讲交接时为什么会暴露更多责任。结构按工程难点推进，不再按 LRS→HLD→LLD→RTL 的步骤讲一遍，不重复配置锁与 VIP 读写同错两个主案例。Skills 在后半篇作为应对方法出现，不做工具生态介绍。

## 主案例选择

主案例选 SPI2APB：用外部 SPI 串行命令访问片内 APB 外设。正常读写容易解释，首读、校验、缓存、停钟、中止和驱动重试能自然展示“功能之间的关系”。

只用一个辅助案例：WDT（看门狗）的复位请求必须接到能够执行恢复的系统实体。用来说明职责边界；它是集成要求，不虚构成已经发生的接线失败。

不把多个项目的问题汇成缺陷目录。每个难点都配合说明已采取的修正、检查或交付约定，让文章展示解决问题的方法。

## 推荐开头（约 300 字）

从“增加保护，却让第一笔读取失败”起笔。SPI2APB 给待发命令增加奇偶校验后，上电第一条 READ 暴露了未初始化写缓存的依赖。READ 没有写载荷，命令准备却仍取出写缓存数据；四态仿真中的未知值 X 进入校验路径，影响命令发出。修正将 READ 的数据字段与对应校验输入一起固定为零，原场景复验后进入完整回归。

可用开场：

> 一款桥接 IP 给内部命令增加了完整性检查，上电后的第一笔读取却失败了。READ 本来不需要写数据，但命令准备逻辑仍从写缓存取值；这份尚未初始化的数据进入校验，影响了读取命令。
>
> 如果测试总是先写再读，这个依赖很容易被掩盖。这个问题提醒我：当我们把一段 RTL 交给下一个项目时，还要交代它依赖哪些前提，以及这些前提怎样得到检查。

这是根据记录组织的叙述，不添加“几分钟生成”“交付当天”“客户现场出错”等没有来源的情节。

## 正文：四类难点，再落到 AI 怎样参与

### 1. 正常读写只是起点，状态切换决定使用边界（约 650 字）

先解释 SPI2APB 两端的角色，再追问一笔访问被打断时的行为：权限撤销、SPI 中止和 APB 复位是否按同一种方式处理？

采用工程中明确的两种情况：普通 SPI/片选中止不能随意掐断活动 APB 拍，应完成当前拍后停止新拍；APB 复位则存在外设已产生副作用、桥尚未采到完成的不确定边界。两者影响软件能否重试。

因果主线：正常通路检查“能不能读写”；异常约定还要说明“已经发生了什么、还允许发生什么、怎样恢复”。AI 可以展开场景和修改实现，工程师先决定符合系统需要的语义。

不是所有细节都来自协议默认答案，例如业务是否允许自动重试还与外设副作用有关。本文只讲本工程的策略，不推广成所有桥接 IP 的统一要求。

### 2. 一个局部改动，会改变别处的前提（约 750 字）

详细解释首读案例：宽缓存不整体复位，原本不该供 READ 使用的字段进入新校验路径，形成隐藏依赖。保留缓存实现方式，将 READ 无效载荷规范化为零，并让数据字段与校验输入采用相同值。

配因果图：上电 → 写缓存未知 → READ 取了无关数据 → 校验受影响 → 命令受阻；修正后 READ 使用确定的零值。

重点是功能之间的影响。复位、校验、缓存和命令准备单独看都容易描述，组合后必须确认不变量仍成立。再举一个方法层面的例子：修改缓存深度，可能同时影响索引、满空判定、计数位宽和边界测试，但不捏造本项目发生过这组缺陷。

AI 的作用落在读取关联逻辑、定位首个失败、同步修改数据和校验输入、补首读回归。不能仅凭代码和测试都是 AI 写的就宣称独立验证。

### 3. 参数写进 RTL 后，验证责任会跟着扩展（约 650 字）

解释参数会改变边界、结构和协议能力。默认配置成功不能代表最小、最大及其他组合成立。展开检查回答生成后的结构是否合法；功能仿真检查施加的场景；综合评估特定配置和约束下的实现代价，三者不互相替代。

这里可以使用一组非常克制的数据：SPI2APB 报告记录 **48 个合法组合通过展开检查**；功能回归采用 **APB3/APB4 各四种 SPI 模式，共 8 个命名配置**。不要写成“48 配置全功能通过”。数据对应报告的 closure_final05，seed=17；VCS W-2024.09-SP1。详细矩阵和其他工具版本保留在内部证据中，需要引用综合结果时再补对应条件。

正文将这两个数字放在一张小表里，回答“测试究竟覆盖了哪一层”。不罗列全部故障注入、覆盖率和通过数。

方法是明确支持配置、安排边界/风险组合、记录每配置实际检查结果，并拒绝不支持的输入。选择代表点不等于证明其余全部组合。参数空间 Skill 可作为这些做法的载体；存在 Skill 本身不构成执行证据。

### 4. 交到下一套系统里，隐含假设必须变成明确约定（约 800 字）

接收方面对的不只有端口名：时钟什么时候可停，复位怎样释放，跨域数据怎样保持，哪些约束需要落到实际实现，软件遇到部分完成怎样处理？

继续用 SPI2APB：多拍写可能部分完成，已经执行的外设操作不会因中止自动回滚；驱动不能无条件重发全部命令。讲清这一条，就能把 RTL、状态信息、软件和集成说明连起来。

WDT 用约一段作旁证：模块可以输出复位请求，但系统要把它接到真正执行动作的复位管理器；接口复位和持续监督状态也有不同边界。按集成说明讲要求，不说某个系统已经因此失效。

约束文件同样承担工程信息，跨时钟域数据稳定性不能被一个宽泛的 false path 掩盖。为跨方向读者解释 CDC（跨时钟域）与 STA（静态时序分析）各检查什么；本文不展开具体命令与路径。

交付同时需要冻结源码/依赖版本、支持范围、构建复验入口及限制。哈希确认版本对应关系，打包校验确认包的完整性，二者均不产生新的功能正确性证据。当前 Skill 的本地原始证据策略不能写成接收方解包后无需运行就能重新验收。

### 5. AI 可以继续承担哪些工作？（约 600 字）

给出与前文一一对应的做法，连贯叙述，不重新列完整流程：

- 从一句功能要求展开复位、取消、超时和部分完成的具体问题；工程师确定策略。
- 沿依赖关系寻找受影响的实现、驱动、约束和检查，而不是只盯报错文件。
- 把隐藏前提变成定向测试，将失败反例保留为后续回归。
- 执行并整理配置矩阵，用实际工具结果修正判断，说明未覆盖范围。
- 更新使用说明和版本记录，让接收方能按约定重新检查。

这些内容在正文可压成三段，以本案例已经完成的修正和方法为支撑。没有对照实验就不声称 AI 带来多少倍提效，也不把跨域、功能安全或形式验证列成所有 IP 一律必须做的同一张清单。

### 结尾（约 250 字）

回到首读案例：READ 不再依赖未初始化写缓存，回归保留了这个场景，后来增加保护逻辑时也有一个需要复查的问题。这是一次修复同时改善实现与后续工作起点的具体结果。

最后把“完成”的判断交还给明确使用范围：接收方能否知道在什么条件下使用、按什么入口检查、出现异常怎样处理。下一步关注交接中的假设管理和变更后的复验，不宣称 IP 在所有系统中都已得到保证。

## 素材核对与边界

- SPI2APB `reports/report.md` 的 F-BUF-002 与失败批次说明支撑首读故事。当前报告记录 IP 级完成范围，但不支持无条件正式发布、完整物理时序与高级 CDC/RDC 签核。正文在提到成果时用一句话交代“这里讨论已记录的 IP 级设计与验证结果，系统实现仍需完成对应检查”，不复制内部未完成事项清单。
- 48 是展开组合数，8 是功能回归命名配置数；二者的验证深度不同，不构成矛盾，也不能互换。成稿若引用数字，应再核查矩阵、执行摘要及来源基线。本轮读到的是保存的报告，不是重新执行结果。
- SPI2APB 集成说明明确普通中止与 APB 复位不同、已完成副作用不回滚、禁止自动重放、跨域与物理约束另行检查。不要把普通中止的“当前拍完成”套到 APB 复位上。
- WDT 集成说明支撑复位执行者、独立监督时钟和接口复位边界；不用它证明本轮完成了系统级安全验收。
- 发布 Skill 支撑包完整性、版本与证据分工的当前方法；不把规则当作所有历史 IP 已满足的事实，也不将参考仓的审批要求用于本博客规划。
- 没有“RTL 生成耗时占比”“交付工时占比”或与人工团队的对照材料，正文不写比例和倍数。不能仅凭开发报告将每次发现与具体 AI 模型逐项归因。
